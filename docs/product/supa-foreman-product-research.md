# Mira 速趴工头：产品定位与研究结论

> 状态：产品研究结论（用于指导后续设计与技术验证，不等同于已批准的实现合同）
> 日期：2026-11-04
> 所属项目：`uichat-mira/mira-dsh-plugin`
> 产品名称：Mira 速趴工头（Mira Supa Foreman）

## 1. 结论摘要

**速趴工头是运行在 DeepSeek Harness（DSH）中的工程协作调度插件。它把 GitHub Issue 中的工程任务，转化为可分析、可编排、可观察、可追踪的 DSH 多 Agent 施工过程。**

它不是另一个代码 Agent，不是新的项目管理系统，也不应该重新实现 Agent Teams 或 Git Worktree。它的核心价值是补上现有施工能力之上的调度层：

- **监听**：持续发现符合约定标记和格式的 GitHub Issue。
- **分析**：理解任务合同、依赖关系和实际代码，判断任务是否具备施工条件。
- **派工**：调用 DSH 线程，在一个线程内组织 Agent Teams 和隔离的 Git Worktree。
- **追踪**：把任务、线程、团队成员、工作树、提交、PR、检查和异常串成可观察的执行 Trace。
- **收敛**：汇总施工结果、测试和 Review 证据，给出下一步建议。

一句话：**GitHub 负责定义要做什么，速趴工头负责组织谁来做、在哪里做、做到哪里，以及结果是否可追溯；真正的施工由 DSH 和 Agent Teams 完成。**

## 2. 要解决的问题

目前工程协作的主要瓶颈已经不只是 Agent 的编码能力，而是人需要持续承担大量协调工作：

1. 从大量 Issue 中识别哪些任务已经可以开工。
2. 阅读任务背景、仓库规则、现有代码和依赖，判断是否适合施工。
3. 决定哪些任务可以并行、哪些必须串行，以及如何分配文件所有权。
4. 启动 DSH 会话、组织 Agent Teams、隔离 Git 工作区。
5. 持续检查 Agent 是否运行、卡住、失败、返工或完成。
6. 汇总提交、测试、PR 和 Review 证据，避免重复派工和任务漂移。

Agent Teams 已经提供了相当成熟的团队施工基础，DSH 也已具备原生线程和 Worktree 能力。速趴工头不应重复造这些轮子，而应把它们组织成一条稳定的工程交付链。

## 3. 核心产品能力

### 3.1 监听：发现候选任务

通过定时器或轻量轮询，扫描指定 GitHub 仓库中符合约定标记的 Issue。

监听阶段只负责低成本发现与初筛：

- 识别约定的 Issue 标头、标签或其他触发标记。
- 检查必要字段和任务合同格式。
- 排除已关闭、已在施工、已有活动 PR 或明显不完整的任务。
- 对重复事件进行去重，避免同一任务反复触发。

**格式检查应先于复杂模型分析。** 不合格任务给出明确原因，不消耗完整编排模型额度。

具体采用什么 Issue 标头、标签和字段格式尚未冻结，应在后续设计中定义为可配置的任务入口合同；不能在实现中自行假定某一种格式已经成为组织标准。

### 3.2 分析：由编排 Agent 判断如何施工

通过初筛后，触发编排 Agent。它不必是最轻量的模型；应根据任务复杂度选择足够可靠的模型。

编排 Agent 应先读取：

- 当前组织级规则和目标仓库规则；
- Issue 正文、关联 Issue、PR、评论及已有执行记录；
- 相关源码、测试、配置和架构边界；
- 任务依赖、冲突文件、并行可能性和外部阻塞。

分析结果至少应包含：

- 任务是否具备施工条件，以及证据和阻塞原因；
- 任务拆分与依赖 DAG；
- 每个子任务的目标、验收条件和文件所有权；
- 可并行成员数量及工作树隔离策略；
- 预计调用的 DSH 线程和 Agent Teams 执行方案。

编排 Agent 应能判断“不派工”。信息不足、目标冲突、依赖未满足或风险过高时，明确停下来，而不是为了让流水线持续运行而强行开工。

### 3.3 派工：调度 DSH 线程，而不是另造执行器

**已确定的技术方向：调用 DSH 线程，不以 DSH Super Agent 作为施工入口。**

速趴工头负责组织和调度；DSH 线程承载一次施工会话；Agent Teams 在该线程内负责团队编排；各成员使用独立 Git Worktree 施工。

不重新实现：

- Agent Teams 的成员、任务 DAG、消息与协作机制；
- Git Worktree 的创建、隔离和切换；
- Agent 的代码执行、测试和提交能力。

优先复用 DSH 已提供的原生能力。只有在真实运行验证发现缺少必要接口时，才考虑补充最小适配层。

### 3.4 一个线程承载多张卡

**产品上允许一个 DSH 线程组织多张相关任务卡的协同施工。** 线程是一次协作会话的容器，不是任务真相源。

需要保持以下边界：

- 每张 Issue 都保留独立的任务合同、验收条件和状态。
- 编排层明确任务之间的依赖、共享上下文和冲突关系。
- Agent Teams 可以在一个团队内处理多个相关任务，但每个子任务必须有明确负责人和文件所有权。
- 每个 Agent 使用独立 Worktree；不得因共享线程而共享可写工作区。
- 一张卡失败、取消或被阻塞，不应让无依赖关系的其他任务失去可恢复性。
- 同一张卡不能被多个执行批次重复派工。

是否将多张卡放入同一个线程，应由任务关联性、依赖和上下文共享价值决定，而不是简单地把所有待办塞进一个线程。

### 3.5 监听运行与追踪 Trace

监听器与执行监控不是一回事：

- **监听器**发现新的候选 Issue，是轻量、低成本的入口 Agent。
- **运行监控**跟踪已经启动的 DSH 线程、Agent Teams 任务和 Git Worktree 状态，优先使用状态事件或低成本轮询，不应持续调用强模型。

每次派工应生成唯一的执行批次标识，并形成可追溯的事件链：

`Issue → Dispatch Run → DSH Thread → Agent Team → Member Task → Worktree → Commit → PR → Checks / Review`

Trace 至少记录：

- 触发来源、候选任务和格式检查结果；
- 编排分析结论、派工计划及批准记录；
- DSH 线程标识、Agent 成员、任务依赖和 Worktree 路径；
- 开始、心跳、完成、失败、超时、取消和重试事件；
- 分支、提交 SHA、PR、测试与 Review 证据；
- 人工干预、暂停、拒绝、返工和最终处置。

Trace 是运行审计与恢复依据，不是第二套项目管理台账。GitHub Issue 仍是任务合同和任务结果的权威来源；Trace 记录执行过程及其关联关系。

### 3.6 交付收敛

Agent Teams 完成后，工头负责收集结果并组织集成验证：

1. 检查成员任务是否全部进入终态。
2. 检查分支和 Worktree 是否完整、是否存在未提交改动。
3. 按依赖关系集成并运行必要测试。
4. 触发或等待适用的 Review，汇总实际问题。
5. 将结果、证据和遗留风险回写到对应 PR / Issue。

工头可以给出“可合并”“需要返工”“等待外部条件”等建议，但不能把 CI 绿灯直接等同于功能验收。

## 4. 已确认的产品与技术决策

| 决策 | 当前结论 |
| --- | --- |
| 产品形态 | DSH 插件，工程协作调度层 |
| 任务真相源 | GitHub Issue / PR，不另建任务台账 |
| 施工入口 | DSH 线程，不调用 DSH Super Agent 作为施工入口 |
| 团队执行 | 复用 DSH 中的 Agent Teams |
| 工作区隔离 | 复用 DSH 内置 Git Worktree |
| 监听成本 | 轻量监听器先做标记和格式初筛 |
| 深度判断 | 由具备足够能力的编排 Agent 阅读需求与源码 |
| 多卡协作 | 相关任务可由同一个 DSH 线程中的 Agent Team 协同完成 |
| 可观察性 | 每次派工形成完整 Trace |
| 合并与收卡 | 可作为后续可选能力，不是初期自动化前提 |

## 5. 权限与人工控制边界

速趴工头可以自动发现任务、分析任务、生成派工计划，并在获得明确授权后调度施工。

**当前阶段，是否应该派卡、是否应该阻止派卡，仍由 Mira / 维护者把关。** 这项产品裁决权暂不交给插件自行决定。插件必须把分析依据、风险和计划展示出来，不能通过定时器或模型输出绕过人工把关。

同样地：

- 任务格式通过不等于获得施工授权。
- 编排 Agent 建议派工不等于派工已获批准。
- Agent Teams 完成不等于 PR 已验收。
- CI / Review 通过不自动授予合并权。
- 合并、关闭 Issue、晋级和部署是独立的高影响动作；初期默认只给出建议，只有获得明确授权后才能执行。

## 6. 建议的演进顺序

以下是研究建议，不是已冻结的版本承诺。

### 阶段 A：任务入口与分析

- 定时扫描可配置仓库和触发标记。
- 对 Issue 做确定性的格式检查、去重和基础状态过滤。
- 调用编排 Agent 读取任务合同、依赖和相关源码。
- 展示任务分析、阻塞原因、拆分 DAG 和派工计划。
- 保留人工批准入口，不自动派工。

### 阶段 B：真实 DSH 线程调度

- 验证并接通 DSH 的线程创建、选择或恢复接口。
- 在一个 DSH 线程中启动 Agent Teams。
- 为不同 Agent 创建独立 Worktree，落实文件所有权和依赖关系。
- 支持一张卡与多张相关卡两种施工模式。
- 建立执行批次 ID、事件记录和基础 Trace。

### 阶段 C：持续监控与恢复

- 观察线程、成员任务和 Worktree 的运行状态。
- 识别长时间无进展、失败、超时和外部阻塞。
- 支持暂停、取消、有限重试和人工接管。
- 保证重启后能够从持久化 Trace 恢复状态，不重复派工。

### 阶段 D：交付收敛

- 汇总提交、PR、测试、Review 和遗留问题。
- 组织集成验证和返工。
- 给出合并、收卡建议。
- 在明确授权和可靠证据前提下，再评估可选的合并、Issue 关闭等动作。

## 7. 需要通过真实运行验证的技术问题

以下事项不能仅凭产品设计推断为 DSH 已支持：

1. DSH 是否提供稳定、受支持的线程创建、线程选择、线程恢复和消息注入接口。
2. 插件能否在不模拟 GUI 点击的情况下，可靠地调度一个指定 DSH 线程。
3. Agent Teams 是否能从插件或 DSH 线程上下文中启动、查询、暂停和恢复。
4. 一个 Agent Team 是否能稳定地承载多张 Issue，并保持每张卡的独立任务合同。
5. 内置 Worktree 能否提供可查询的创建、分配、回收和异常恢复状态。
6. DSH 线程、Agent Teams 和 Worktree 的运行事件能否被插件可靠订阅；若不能，轮询成本和延迟是否可接受。
7. DSH / Agent Teams 重启后，线程、任务和工作树之间的关联如何恢复。
8. GitHub 凭证如何以最小权限提供给调度层和 Worker，避免不必要地暴露写权限。

这些验证应围绕真实 DSH 运行链路进行。若原生能力不足，优先做小型适配验证，不提前建设一套自有 Agent Runtime。

## 8. 成功标准

速趴工头是否成功，不以面板有多少页面、Agent 数量或自动化步骤衡量，而以一条真实交付链是否可靠为准：

- 能从指定 GitHub Issue 入口发现并正确识别候选任务；
- 格式不合格、依赖未满足或已有执行中的任务不会被误派；
- 编排 Agent 能基于实际源码给出可执行的任务 DAG；
- 经批准后能调度 DSH 线程和 Agent Teams；
- 多个 Agent 在独立 Worktree 中完成各自任务；
- 同一线程内多张相关卡仍能独立追踪和恢复；
- 失败、重启、取消和重试不会造成不可解释的重复施工；
- 从 Issue 到 PR 的执行 Trace 完整、可检查；
- 人可以随时理解当前进度，并保留派工否决与高影响动作控制权。

## 9. 当前实现基线与本研究的关系

截至本文记录时，仓库 `dev` 分支已有的能力是一个只读工程上下文插件：

- `mira_issue_contract`：读取当前组织规则、仓库规则和 Issue 合同；
- `mira_pr_evidence`：读取 PR 当前提交、检查和 Review 证据；
- `mira_task`：关联 Issue / PR 并给出保守的下一步建议；
- `mira-task inspect`：提供 CLI 只读检查入口。

PR #1（Draft）提出了 DSH 原生只读面板，包括任务概览、验收证据和连接状态。它不包含自动监听、编排、派工、运行监控或 Trace。

因此，本文描述的是**下一阶段产品方向**，不能把监听、调度、Agent Teams 自动启动、多卡协作和完整 Trace 写成当前已交付能力。

## 10. 当前不做的事

- 不自研 Agent Teams、Agent Runtime 或 Worktree 引擎。
- 不以 DSH Super Agent 作为施工调度入口。
- 不建设第二套 Issue / PR / 项目任务台账。
- 不在缺乏证据时自动创建任务、重复派工或扩大任务范围。
- 初期不自动合并 PR、关闭 Issue、晋级或部署。
- 不为展示自动化程度而引入多层模型 Agent；优先使用确定性规则和现有 DSH 运行状态。

---

**最终定位：速趴工头不是替代工程师的超级程序员，而是让 DSH 中已有的多个 Agent、多个 Worktree 和多个工程任务，形成一条可控、可观察、可恢复的施工流水线。**
